### [Decisions API is in public beta](https://news.ycombinator.com/item?id=49984025)

- **HN engagement:** 348 points, 188 comments
- **Primary topic:** OpenAI Decisions API public beta for structured probability-based classification
- **Evidence basis:** source-and-discussion
- **External page:** success
- **Source:** https://developers.openai.com/api/docs/guides/decisions

The API offers a cheaper path to binary or categorical classification by charging only input tokens and returning structured probability scores without generating output text. However, the position-bias finding from one commenter's experiments raises practical concerns about reliability for choice-type questions in production routing pipelines.

**Linked source:** The OpenAI Decisions API documentation describes an endpoint at `/v1/decisions` that accepts structured question arrays of type predicate, choice, or score, and returns probability distributions rather than generated text — with pricing at $0.10 per 1M input tokens using gpt-6-luna and zero output-token charges. The source states that choice and score answers include a `confidence` field and a per-level probability distribution, and recommends using labeled examples to set routing thresholds based on false-positive and false-negative costs.

**HN discussion:** One commenter (simonw) shared a live curl example showing the API returning predicate probabilities with zero output tokens consumed, confirming the input-only billing model. One commenter (armcat) ran 1,000-trial experiments and found that choice questions exhibit significant position bias — reordering choices measurably changed probability estimates — while predicate questions produced nearly expected outcomes.

### [Shipping JPEG XL in Chrome](https://news.ycombinator.com/item?id=49991227)

- **HN engagement:** 140 points, 68 comments
- **Primary topic:** Chrome shipping JPEG XL decoding support via a Rust-based decoder
- **Evidence basis:** source-and-discussion
- **External page:** success
- **Source:** https://developer.chrome.com/blog/jpeg-xl-in-chrome

Chrome's prior removal of JXL support had created a de facto blocker for web deployment, so re-shipping it with a Rust decoder directly affects decisions about image pipeline modernization. The coexistence of JXL and AVIF also leaves developers needing guidance on which format to use in which scenario.

**Linked source:** The Chrome developer blog announces JPEG XL decoding support starting in Chrome 155, highlighting the use of a pure Rust decoder (jxl-rs) for memory safety, SIMD-based performance work informed by the C++ Highway library, and developer feedback channeled through the Interop 2026 project. The source claims jxl-rs achieved no memory safety bugs throughout its implementation history and that JPEG XL offers 30–50% better compression than JPEG with additional features such as lossless JPEG transcoding and HDR support.

**HN discussion:** Commenters are broadly positive about Chrome re-adding JXL support after its prior removal, with one commenter noting that Chrome's absence had significantly limited JXL's web adoption. Several commenters raised ecosystem readiness concerns—app-level support in tools like Telegram and OS-level support lagging behind browser adoption.

### [Claude Code’s suggested message feature: I think the real customer is the model](https://news.ycombinator.com/item?id=49981905)

- **HN engagement:** 233 points, 132 comments
- **Primary topic:** Claude Code's suggested-message feature analyzed as potential RLHF data-collection mechanism
- **Evidence basis:** source-and-discussion
- **External page:** success
- **Source:** https://www.zohaib.cc/blog/smartest-claude-code-feature

Developers using AI coding assistants have a direct interest in understanding whether their interactions—including edits to suggested prompts—are feeding model training, since this affects both privacy expectations and trust in feature design rationale. The public contradiction between the blog's hypothesis and an Anthropic employee's denial highlights uncertainty about how these systems actually use behavioral signals.

**Linked source:** The blog post argues that Claude Code's pre-filled suggested-message feature is primarily valuable to Anthropic as a low-cost RLHF data-collection mechanism: sending the suggestion unchanged acts as a positive label, while editing it produces a preference pair showing exactly where the model's prediction diverged from what a real developer wanted. The author explicitly notes this is speculation, and an Anthropic employee (edwinarbus) replied on HN denying the hypothesis, stating the feature was built purely for user flow and that suggestion-acceptance data is used only to measure the feature's helpfulness.

**HN discussion:** HN commenters were divided: some supported the RLHF-collection hypothesis on technical grounds, while others questioned whether showing the suggestion to users actually biases the signal and undermines its independence as training data. One commenter noted surprise that the Anthropic reply flatly rejected the framing.
