### [Decisions API is in public beta](https://news.ycombinator.com/item?id=49984025)

- **HN engagement:** 346 points, 184 comments
- **Primary topic:** OpenAI Decisions API public beta: probability-based predicate and choice questions via a dedicated endpoint
- **Evidence basis:** source-and-discussion
- **External page:** success
- **Source:** https://developers.openai.com/api/docs/guides/decisions

The API offers a cheaper, output-token-free path for classification and routing tasks, but the ordering bias discovered in choice questions raises reliability concerns for production use. Developers are also weighing whether the cost savings justify switching from standard LLM calls when models like gpt-6-luna are already inexpensive.

**Linked source:** The OpenAI documentation describes the Decisions API as a dedicated endpoint (`/v1/decisions`) that accepts predicate, choice, and score question types against shared input, returning probability distributions rather than generated text; with `gpt-6-luna` it costs $0.10 per 1M input tokens with no output-token charges, and it supports Zero Data Retention, HIPAA, and regional processing for eligible customers.

**HN discussion:** One commenter (simonw) shared a live curl example showing the API returning probabilities for predicate questions with zero output tokens billed, confirming the input-only pricing claim. One commenter (armcat) ran thousand-trial statistical experiments and found that while predicate questions produced near-expected probabilities, choice questions exhibited significant ordering bias—moving a choice from first to last position shifted its estimated probability from 86% to 73%.

openTPU demonstrates a full AI accelerator stack—from RTL to compiler to host driver—reportedly generated by AI agents, making it both a concrete existence proof of AI-assisted chip design and a self-contained learning resource. The DRAM-bound inference results and open monorepo structure give hardware-curious developers a rare end-to-end reference implementation they can read and modify without proprietary tooling.

The project claims to run ten modern models (including Qwen3, LFM2.5, Gemma 4, Phi-4-mini, and SmolLM3) at decode speeds ranging from ~4 to 86 tok/s depending on model and quantization, with DRAM utilization reaching up to 94% of DDR3-1066 peak.

### [Shipping JPEG XL in Chrome](https://news.ycombinator.com/item?id=49991227)

- **HN engagement:** 122 points, 54 comments
- **Primary topic:** JPEG XL shipping in Chrome via a Rust-based decoder
- **Evidence basis:** source-and-discussion
- **External page:** success
- **Source:** https://developer.chrome.com/blog/jpeg-xl-in-chrome

Chrome's support removes the biggest blocker to deploying JPEG XL on the web, and the Rust-based decoder (jxl-rs) is notable as a case study in achieving memory safety without sacrificing SIMD performance in a security-critical code path. However, uneven support across Safari, apps, and OS image viewers means ecosystem fragmentation remains a practical deployment concern.

**Linked source:** The Chrome team's official post announces JPEG XL decoding support starting in Chrome 155, highlighting that the decoder was reimplemented in Rust (jxl-rs) for memory safety, with SIMD performance parity achieved via a new abstraction layer inspired by the C++ Highway library. The decision was driven by consistent developer feedback through channels including the Interop 2026 Project, and the team recommends trying both AVIF and JPEG XL depending on use case.

**HN discussion:** HN commenters reacted positively to the re-addition of JXL support after its earlier controversial removal from Chrome, with several noting the format was previously hampered by Chrome's absence. One commenter raised ongoing concerns about fragmented ecosystem support across apps and operating systems for newer image formats generally.
